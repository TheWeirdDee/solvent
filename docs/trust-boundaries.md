## What Gate 4's "acceptance" does NOT mean

It does not mean a live Cashu mint's HTTP swap/receive endpoint was called, and it does not mean a full wallet was built. It means: SOLVENT's own decision boundary performs a real, observable state mutation (real token serialization + a committed local record) if and only if the decision was `ACCEPT`, and performs nothing at all on `REFUSE` — proven by a real function-call spy, not by inspection of source code.

## NOT YET REAL in this build

- **Wallet-redeemable tokens.** `createTestEcash()` (and every "Try SOLVENT" scenario) produces a genuine NUT-00-compliant *encoded* Cashu token via `@cashu/cashu-ts`'s real `getEncodedToken()` — any NUT-00-compliant parser can decode it. But its `mint` field is `solvent-fixture-mint`, a SOLVENT-internal label, not a reachable HTTP mint URL. There is no live mint server behind it, so a real wallet could parse the token but could never redeem/swap it. SOLVENT's own copy calls this "SOLVENT test ecash," never "a real Cashu token you can spend" — see `docs/verification-bundle.md`'s "Is this ecash real?" section for the full answer this build gives to that question.
- **OpenTimestamps anchoring**, BLS12-381 receipts, keyset-lifecycle enforcement, the optional Nostr "latest state" pointer event, and three of the five PR #388 fraud-challenge types — see `docs/draft-alignment.md` for the complete, itemized list.
- **Full BIP-322** proof-of-funds — Gate 6 uses the PRD §11.2 bounded alternative instead (see `docs/reserve-attestation.md`), not full BIP-322; nothing in this build is labeled "BIP-322."
- **Publishing a fresh Nostr event on every Create Test Ecash click.** Create Test Ecash mints a brand-new random identity every run, specifically to prove genuine fresh issuance — publishing a throwaway event to production relays on every button press would spam them for no real benefit, so it doesn't. See "The two-tier Nostr guarantee" below for exactly what that means for its verification result.

## The two-tier Nostr guarantee

Earlier builds of this pass let a cryptographically valid signed event that a bundle merely *carried* satisfy the Nostr check, even if no public relay had ever seen it. That conflated two different claims:

1. **Cryptographic bundle validity** — is the event a genuine, internally-consistent BIP-340 signature over this bundle's own manifest/reserve digests? Real cryptography, but it only proves the *sender* possesses a validly signed event.
2. **Live public acceptance verification** — was that exact accounting state independently *retrieved from a public relay*, right now? This is SOLVENT's actual claim (see `docs/nostr-schema.md`): the mint's accounting is publicly checkable, not just privately signable.

`src/app/submission.ts`'s `evaluateNostrIndependently()` now keeps these strictly separate:

- Every verification (Try SOLVENT, Create Test Ecash, and Verify Your Evidence alike) genuinely attempts a real, multi-relay fetch (`fetchPolEvidence()`, the same call Gate 5 uses) for the bundle's own `(mint_identity, epoch)`, every time, never skipped.
- `providedCopyValid` (informational only, shown in the evidence panel, **never gates ACCEPT**) — is the bundle's own private copy cryptographically valid on its own.
- `publicationVerified` / `verified` (the actual gate fed into `verify()`) — is true **only** when a public relay genuinely returns this evidence. A bundle whose event cannot be found publicly gets a REFUSE — even when its own private copy is perfectly valid. There is no fallback path from "cryptographically valid" to "accepted" that skips public retrieval.

**Two distinct REFUSE reasons, never collapsed into one:**

| Reason code | Means | Relay was... |
| --- | --- | --- |
| `REFUSE_NOSTR_UNAVAILABLE` | No configured relay could be reached at all — SOLVENT cannot establish public publication either way. | Unreachable (network failure) |
| `REFUSE_NOSTR_EVENT_NOT_FOUND` | At least one relay was reached successfully, but none returned the required evidence for this mint/epoch. | Reachable, evidence genuinely absent |

These are materially different claims ("we couldn't check" vs. "we checked and it isn't there"), and the UI never conflates them — see `nostrLive.relayReachable` in `src/app/submission.ts`. `REFUSE_NOSTR_CONFLICT`/`REFUSE_NOSTR_STATE_MISMATCH`/`REFUSE_NOSTR_STALE` remain unchanged for their existing, more specific cases (a relay actively returning conflicting, mismatched, or expired signed state).

**How `relayReachable` is actually determined:** `nostr-tools`' `pool.querySync()` never rejects on a connection failure — it resolves with whatever it collected (possibly nothing) once its timeout elapses, even if every relay was completely unreachable. A naive "did the fetch call throw" check would therefore never see a real network failure and `REFUSE_NOSTR_UNAVAILABLE` would be effectively dead code on the real network path (this was caught and fixed during this build, not a hypothetical — verified with a real browser test that closed the relay WebSocket connections and confirmed the UI correctly showed "PUBLIC EVIDENCE COULD NOT BE CHECKED" rather than collapsing into "PUBLICATION NOT FOUND"). `fetchPolEvidence()` (`src/nostr/pol-evidence.ts`) instead listens for `SimplePool`'s own `onRelayConnectionSuccess` callback, which fires at the exact moment a relay's connection genuinely succeeds — real reachability, not an inferred proxy for it.

Consequence: **Create Test Ecash's own verification correctly cannot reach `ACCEPT_VERIFIED`** — every real gate up through reserve coverage passes, but its event was never published, so `Exact event: NOT FOUND` and the decision is `REFUSE_NOSTR_EVENT_NOT_FOUND` (relays are genuinely reachable in this build's normal operation; only a real network outage would produce `REFUSE_NOSTR_UNAVAILABLE` instead). The UI shows this as "CRYPTOGRAPHIC CHECK PASSED / PUBLICATION NOT FOUND," not a scary generic refusal, with a link to the Live Public Demo. This is intended, correct behavior, not a bug: it is the whole point of the distinction.

### Bounded relay-fetch retry

A real relay miss can be transient — observed directly during this build: the Live Public Demo's genuinely-published, genuinely-findable event once came back `NOT FOUND` on a fresh verification, then `FOUND` on three immediate repeats. `evaluateNostrIndependently()` (`src/app/submission.ts`) now performs exactly one bounded retry, after a short delay, whenever the exact event wasn't found on the first attempt (regardless of whether that first attempt showed the relay reachable or not — a first-attempt outage can also be transient). Reachability and fetched events from both attempts are combined (reachable if *either* attempt reached a relay; events are the union of both, deduped downstream by the unchanged `evaluatePolEvidence()`), so a conflicting event that only shows up on the retry is still correctly caught as `REFUSE_NOSTR_CONFLICT`, not silently dropped. This never converts a genuinely unpublished event into a false `ACCEPT`: if the event still isn't found after the one retry, the result is exactly what a single attempt would have reported. Exactly one retry, never more — a real outage still refuses in bounded time (~1.5s added latency, only on a miss; the common healthy-path case where the event is found on the first attempt pays no extra latency at all). Tested deterministically for all five required cases (found-on-retry, still-not-found, both-unreachable, unreachable-then-found, conflict-on-retry) in `src/app/main.test.ts`'s "bounded relay-fetch retry" suite, using an injected sequence of mocked fetch results — no real network or sleep in the test.

### Effective expiry — the real number, and the network-aware fix behind it

Two independent freshness windows bound this demo, and **the shorter one wins**:

1. **Nostr event freshness** (`isPolEvidenceFresh()`, `src/nostr/pol-event.ts`): `now` must be within `[issued_at, valid_until]`. `live-demo.ts` sets `validitySeconds` to 30 days, so this window is `publishedAt + 30 days` — never the binding constraint below.
2. **Reserve attestation freshness** (`evaluateReserveAttestation()`, `src/reserve/evaluate.ts`): refuses once `currentTipHeight - statement.block_height` exceeds a budget. **This budget is now network-aware, not a flat constant.**

**What the 1008-block figure actually meant, and why a flat count was a bug, not a policy.** The original constant's own comment read `1008; // ~1 week at 10min blocks; generous on purpose`. 1008 is *exactly* 7 days × 144 blocks/day at Bitcoin's standard ~10-minute block target (`7 * 24 * 6 = 1008`) — i.e., the intended security property was always **a generous ~1 week of real elapsed time**, expressed as a block count under a mainnet/default-signet cadence assumption, not "1008 blocks, whatever network." Mutinynet was deliberately chosen for this build for its fast ~30.5s blocks (see `docs/reserve-attestation.md`'s "Network" section — a same-session-confirmation convenience, unrelated to the staleness policy), so reusing the same raw 1008 there silently enforced a real window of only **~8.5 hours** — a ~68x tighter budget than intended, and the actual root cause of the Live Public Demo needing manual regeneration every few hours. This was a bug in the constant's portability, not an intentional policy choice, and independently-verified block height (never a self-reported timestamp on the statement) is still the right staleness clock — a mint could misstate its own `timestamp` field, but not how far the real chain has actually advanced.

**The fix:** `ReserveFreshnessPolicy` / `maxAttestationAgeBlocks(network)` (`src/reserve/evaluate.ts`) replaces the flat constant with a per-network block budget sized to hit the same real ~1 week target regardless of block cadence: `targetSeconds / secondsPerBlockByNetwork[network]`. On `bitcoin-mainnet`/`bitcoin-signet` (~600s/block) this is still exactly 1008 blocks — no behavior change there. On `bitcoin-signet-mutinynet` (~30.5s/block, empirically measured via 10 real consecutive block timestamps from `mutinynet.com`'s own Esplora API) it's **~19,830 blocks**, restoring the real ~1 week window. An unrecognized network falls back to the conservative mainnet-cadence assumption (a smaller budget, never a laxer one). `src/app/verifier-panel.ts`'s "Attestation freshness" evidence row and `npm run verify:live-demo`'s display both use this same function — no duplicated magic number anywhere. Tested in `tests/reserve/evaluate.test.ts`'s "network-aware reserve freshness policy" suite.

**Effective Live Public Demo expiry ≈ `publishedAt` + ~1 week** (the reserve leg is still what bounds this demo's lifetime — the fix corrects its *size*, not which leg binds). Confirmed via a real run: `npm run verify:live-demo` reported a freshness budget of 19,829 blocks (~168.0h). Re-run `npm run live-demo:release` (see "Making regeneration safe" below) well before then — the browser UI and `npm run verify:live-demo` both compute and show the actual remaining freshness window from the live evidence file rather than a hardcoded assumption; do not rely on this doc's numbers being current.

### Why the demo mint identity is NOT persisted across `npm run live-demo` runs (investigated, and reverted)

A stable mint identity — generate once, persist like `evidence/reserves/reserve-key.json` already does for the reserve key, and only refresh the reserve attestation + Nostr event on each re-run — was investigated and actually built and tested for real, because it would make the demo more credible (one continuous identity, not a new one every regeneration) and reduce what needs republishing. **It was reverted after real testing proved it breaks the demo.**

Why: kind 8181 is deliberately **regular/immutable**, not NIP-33 parameterized-replaceable (PRD §12.2 — "the audit record must not depend solely on an addressable event a relay may discard/replace," see `docs/nostr-schema.md`). An old published event therefore never disappears from a relay. Publishing a second, fresh reserve attestation under the *same* `(mint_identity, epoch)` leaves the first event permanently co-discoverable, with a *different* `reserve_digest` (the reserve statement changed — new block height). The real, unmodified `evaluatePolEvidence()` (Gate 5) correctly groups fetched events by `(manifest_digest, global_digest, reserve_digest)` and treats two distinct groups for the same identity/epoch as `REFUSE_NOSTR_CONFLICT` — confirmed empirically by actually publishing twice under one stable identity and re-running `npm run verify:live-demo`, which reported exactly that. Loosening that grouping to tolerate this would mean the verifier could no longer reliably catch genuine equivocation (a mint publishing two different real liability claims for the same epoch) — a real fraud-detection property this build is not willing to weaken for demo-maintenance convenience. So `npm run live-demo` mints a genuinely fresh identity on every run, exactly as it always did; only the freshness-policy fix above addresses how often that needs to happen.

### Making regeneration safe

`npm run live-demo` overwrites `evidence/nostr/live-demo.json` and publishes a brand-new Nostr event (and a brand-new mint identity — see above) every time it runs; event id, mint identity, all digests, reserve outpoint binding, `publishedAt`, and the Cashu proof/token all change. Nothing in this repository's docs hard-codes those ephemeral values as prose to keep in sync by hand: this section, `docs/verification-bundle.md`'s example, and the UI all either read the live file directly or explicitly say "see the current `evidence/nostr/live-demo.json`" rather than asserting a specific id is "the current one" — confirmed empirically during this pass by regenerating the demo (twice) and grepping the whole repo for the old event id/digests: zero hits outside the evidence file itself.

**This is bundled at build time, not fetched at runtime — regeneration alone does not update a deployed site.** `protocol-demo.ts` and `submission.ts` both `import liveDemoEvidence from '../../evidence/nostr/live-demo.json' with { type: 'json' }` — a static ES module import that Vite inlines into the production JS bundle at `npm run build` time (confirmed by building and grepping `dist/assets/*.js` for the live evidence's own Nostr event id — found, literally baked in). So refreshing the deployed demo requires, in order: (1) `npm run live-demo` (regenerate + publish), (2) `npm run build` (bake the new evidence into a new bundle), (3) redeploy `dist/`. `npm run live-demo:release` runs steps 1-2 together in one command. Step 3 is automated — see "Automated deployment refresh" below.

**If a judge opens the deployed app after the evidence has expired:** the browser's live re-verification (never cached) correctly detects the reserve attestation's staleness and shows "LIVE DEMO EVIDENCE EXPIRED" with Accept disabled — never a silent `ACCEPT`, never a quietly-bypassed freshness check, and never presented as a generic refusal. `isReserveAttestationExpired()`/`liveDemoExpiredCopy()` (`src/app/verifier-panel.ts`) detect this specifically (distinct from a shortfall or an unrelated REFUSE) and are wired into all three verify modes. This should be an exceptional maintenance failure (the automated refresh below runs daily, well inside the ~1 week window), not something expected in ordinary operation.

### Automated deployment refresh

`.github/workflows/refresh-live-demo.yml` closes the loop end to end, on a schedule (daily, `0 6 * * *` UTC) and on demand (`workflow_dispatch`):

```
npm ci → npm run live-demo → npm run verify:live-demo → npm test → npm run attacks
  → npm run verify:submission → npm run build → deploy to GitHub Pages
  → npm run verify:deployed (real fetch check of the DEPLOYED bundle)
  → npm run verify:deployed:browser (real headless-browser ACCEPT VERIFIED check of the DEPLOYED site)
```

Fail-closed at every step: a failure at any point before deployment means nothing deploys; a failure in either post-deploy check means the workflow itself fails even though a deploy already happened (there is no step that "deploys anyway" on a check failure). **Provider: GitHub Pages**, chosen specifically because it needs zero additional secrets or accounts — deployment authenticates via the workflow's own built-in `GITHUB_TOKEN`/OIDC (`pages: write`, `id-token: write` permissions), not a stored repository secret. Pages was enabled with build source "GitHub Actions" (a one-time repo setting, not part of the workflow itself).

**Refresh cadence vs. freshness window:** the freshness window is ~1 week (network-aware, see above); the refresh cadence is 1 day; the safety margin is therefore ~6 days — a temporary CI outage, GitHub Pages incident, or a skipped run does not immediately take the deployed demo down.

**`verify:deployed` vs. `verify:deployed:browser`:** the former is a lightweight check (fetch the deployed `index.html`, follow its `<script src>` references, confirm the current live-demo Nostr event id is literally present in the served bundle text — proves the deployment picked up the *right build*) — the latter is the strongest available check (a real headless Chromium loads the deployed site, clicks through Try SOLVENT's LIVE PUBLIC DEMO case exactly as a judge would, and asserts a real `ACCEPT VERIFIED` — proves the deployed build actually *works*, not just that it contains the right bytes). Both are ordinary CLI commands (`npm run verify:deployed -- <url>`, `npm run verify:deployed:browser -- <url>`), runnable manually against any URL, not CI-only tooling.

**Manual fallback**, if the workflow is disabled, failing, or an immediate refresh is needed: run `npm run live-demo:release` locally, then deploy `dist/` (for GitHub Pages specifically: push to `main` and re-run the workflow via `workflow_dispatch`, or push directly using the same `actions/upload-pages-artifact` + `actions/deploy-pages` steps by hand / via `gh workflow run`). Documented in `README.md` and `VERIFY_IN_5_MINUTES.md`.

### One canonical source, three callers

Before this pass, the browser, `npm run verify:live-demo`, and `npm run verify:submission` each had a separate notion of "is the Live Public Demo currently good": the browser bundled `evidence/nostr/live-demo.json` at build time, `verify-live-demo.ts` read the same file straight off disk with its own copy of the freshness math, and `verify:submission` didn't look at this file at all — it graded only historical Gate 5/6 evidence (the last `npm run gate5`/`gate6` run), so it was possible for `npm run verify:submission` to report `SUBMISSION READY` while the actual browser-facing demo a judge would click was stale, unreachable, or mismatched.

Fixed by giving all three exactly one loader and one verifier — `loadCanonicalLiveDemoBundle()` / `verifyCanonicalLiveDemo()` (`src/app/submission.ts`):

```
loadCanonicalLiveDemoBundle() / verifyCanonicalLiveDemo()
       ├── browser (protocol-demo.ts's loadLivePublicDemo/runScenario('honest'))
       ├── npm run verify:live-demo (full diagnostic detail, real network)
       └── npm run verify:submission (required "Canonical Live Public Demo" line)
```

Both the browser (bundled by Vite at build time) and CLI scripts (read by `tsx` at run time) resolve the exact same `import ... from '../../evidence/nostr/live-demo.json' with { type: 'json' }` — there is no second file for any caller to drift onto. `npm run verify:submission`'s historical `Gate 5 (live relay evidence, historical)` / `Gate 6 (live Signet UTXO, historical)` lines are explicitly labeled as historical mechanism evidence and are **not** a substitute for the `Canonical Live Public Demo` line, which is a real, right-now call to `verifyCanonicalLiveDemo()` — confirmed empirically: a transient Esplora network blip during this pass made that one line (and only that line) fail on one run and pass on an immediate re-run, exactly as a live check should. `SUBMISSION READY` is impossible while it fails (`tests/cli/verify-submission.test.ts`).

## What "ACCEPT" from `verify()` means right now

It means: this issuance really came from this mint (real DLEQ), the mint really signed a promise to count it in this epoch (real BIP-340 receipt), that epoch really closed and was really signed (real BIP-340 manifest), the issuance really appears in the signed issued-tree at the claimed value (real sum-MMR inclusion proof), the signed liability arithmetic is internally consistent, and — when `reserve`/`nostr` are supplied by a caller that ran the real Gate 5/6 evaluators (as `src/cli/verify-submission-core.ts` and the attack corpus both do) — that the reserve attestation's signatures/binding/coverage and the Nostr evidence's signature/freshness/digest-binding/non-conflict all independently verified. `verify()` itself stays synchronous and does no network I/O; the real HTTP/relay calls live in `src/nostr/pol-evidence.ts` and `src/reserve/fetch-and-evaluate.ts`, which are expected to run first and then call `verify()` with their result. Omitting `reserve`/`nostr` entirely still fails closed to `REFUSE_UNVERIFIABLE` — verify() never assumes network work happened just because a caller could have done it.

### Why the browser never lets a caller pre-supply `reserve`/`nostr` directly

`verify()`'s `reserve`/`nostr` booleans are trustworthy in the CLI/attack-corpus paths above because the *code calling `verify()`* is the same code that ran the real evaluators — there is no untrusted party in between. That is not true of the browser's "Verify your evidence" flow: the JSON comes from whoever pasted it, and if that JSON could set `reserve: { verified: true }` directly, anyone could paste a fabricated reserve/Nostr claim and get an `ACCEPT` with nothing behind it. So the browser never accepts a `VerifyInput`-shaped bundle from the outside world. It accepts a `SubmissionBundle` (`src/app/submission.ts`) — raw evidence only, with no `verified` field anywhere in its schema — and `verifySubmission()` independently re-derives `reserve`/`nostr` itself (a real live Esplora re-query; a real independent re-check of the raw signed Nostr event's signature/freshness/digest-binding) before ever constructing the `VerifyInput` it hands to the locked `verify()`. See `docs/verification-bundle.md`.
