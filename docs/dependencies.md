## Topology decision: LND for both Lightning nodes, not CLN

CDK's own official regtest environment (`REGTEST_GUIDE.md`, `just regtest`) runs **2 CLN nodes + 2 LND nodes + 2 CDK mints** (one mint per backend) under Nix. Phase 1 uses a **smaller, LND-only topology** — Bitcoin Core regtest + LND-1 (the mint's payment backend) + LND-2 (sender/destination) + one `cdk-mintd` (backend `lnd`, pointed at LND-1) — for two concrete reasons:

1. **Scope**: the Phase 1 plan explicitly says "one real mint is sufficient... do not create unnecessary multiple mint topology yet," and "Lightning Node A" / "Lightning Node B" doesn't require they be different implementations.
2. **Portability**: LND publishes official prebuilt binaries for **Linux, macOS, and Windows** (`lnd-windows-amd64-*.zip` confirmed present on `v0.21.3-beta`); Core Lightning does not publish Windows binaries at all (Linux-only, effectively — see `DEVELOPMENT ENVIRONMENT.md`). Since this project's actual working environment is Windows without Docker/WSL2 (see `docs/real-cashu-stack.md`), an LND-only topology keeps the door open to future local (non-CI) experimentation without requiring WSL2, even though Phase 1's actual verified execution runs in GitHub Actions (Ubuntu) regardless.

CDK's own regtest guide's CLN-based topology remains a legitimate, better-precedented option for a *later* phase if a maintainer wants to exercise `cdk-cln` specifically — nothing here forecloses it; it is simply not needed to satisfy Phase 1.

## Explicitly NOT used in the Phase 1 real path

- **CDK's `fakewallet` payment backend** — real, useful for CDK's own unit tests and for this repo's Lane A (deterministic, no-network) development, but a fake-payment-backend mint cannot produce a genuine "invoice was actually paid" event. `checkRealStackNotFake()` in `src/cli/real-cashu/real-cashu-foundation.ts` explicitly checks the running mint's configured backend and fails closed if it detects `fakewallet`.
- **Docker** — CDK ships Docker images/Compose files (`docker-compose.yaml`, `Dockerfile.ldk-node`, etc.) as one legitimate way to run its regtest stack, and GitHub Actions' `ubuntu-latest` runners do have Docker preinstalled. Phase 1 instead downloads and runs the **prebuilt native binaries directly** (bitcoind, lnd, cdk-mintd) rather than going through Docker — this avoids an extra layer of indirection (image pulls, container networking) on a CI runner that already provides everything natively, and keeps the exact same binaries/flags usable for a future non-Docker WSL2 setup on this project's own development machine.
- **Nix** — CDK's own CI and `REGTEST_GUIDE.md` are Nix-first, with binary-cache-accelerated builds on the CDK maintainers' own self-hosted runners (confirmed by inspecting `cashubtc/cdk`'s `.github/workflows/ci.yml`: every job, including `regtest-ln-itest`, runs on `runs-on: self-hosted`, using a private Cachix/Attic cache this project has no access to). Without that private cache, a from-scratch Nix build of Bitcoin Core + LND + CDK on a stock GitHub-hosted runner would need to compile all of it, which is a real, material time/reliability risk this phase avoids by using prebuilt binaries directly instead.

## Phase 2: no CDK fork, no CDK patch, no rebuild

Phase 2's mint-native accounting (see `docs/cdk-integration-seams.md`, `DECISIONS.md`'s "Phase 2 Step 2" entry) does not modify CDK in any way:

- **Upstream CDK**: `v0.18.1`, exact commit `a056e0f0f69e94f431b1aeb90d883f18c61ea4c6` (same pin as Phase 1 — unchanged).
- **SOLVENT patch**: none. No source patch, no fork, no vendored copy of any CDK crate.
- **Resulting build**: the exact same prebuilt `cdk-mintd` binary download Phase 1 already uses (see the download/checksum step in `.github/workflows/real-cashu-integration.yml`). Phase 2 adds exactly one extra, SOLVENT-owned step after `cdk-mintd ... config init`: apply SOLVENT's own `.sql` migration (SOLVENT-owned tables + triggers — see `docs/accounting-model.md`) directly to the same SQLite file `cdk-mintd` is about to open, before starting the daemon. `cdk-mintd` itself is never rebuilt, patched, or replaced.
- **Reproducibility**: a clean checkout reproduces Phase 2 exactly the way it reproduces Phase 1 (`docs/reproduce-real-stack.md`), plus one documented `sqlite3 <db-file> < path/to/solvent-accounting-migration.sql` command.
