# Limitations — Phase 1

Explicit, not implied. See `docs/REALITY-MAP.md` for the full real/simulated table.

## What Phase 1 does NOT prove

- **SOLVENT's PoL protocol is still not fully connected to any real mint — partially updated by Phase 2.** As of Phase 2 Step 8 closure, real, mint-native PoL *receipt signing, crash-durable recovery, and retrieval* exist for NUT-04 only (`patches/cdk/0001`-`0005`, `docs/cdk-signatory-audit.md`, `docs/receipt-lifecycle.md`, verified in [run 35924475422](https://github.com/TheWeirdDee/solvent/actions/runs/35924475422), [run 35961052740](https://github.com/TheWeirdDee/solvent/actions/runs/35961052740), and [run 35962153613](https://github.com/TheWeirdDee/solvent/actions/runs/35962153613)) — a real CDK mint, patched with real, small source changes, signs real receipts with its real per-amount key, recovers any left `pending` by a real crash, and serves them back over a real retrieval endpoint. Epoch manifests, sum-MMR inclusion proofs, reserve attestations, and Nostr publication are all still produced by SOLVENT's own code against SOLVENT's own freshly-generated identity. NUT-03 (swap) receipt signing and consumed-liability accounting are now real and built (`patches/cdk/0006-*.patch`, `migrations/solvent-accounting/0002_*.sql` — see `DECISIONS.md`'s NUT-03 continuation entry), with real CI verification for that specific work in progress at the time of writing; NUT-05 (melt) receipts do not exist yet. CDK does not implement Cashu PR #388 as a whole (the draft this protocol is built on); no real mint does natively, today — SOLVENT's patch is additive, not upstream.
- **Not evaluated by SOLVENT's verifier.** Phase 1's real proofs/swaps/melts are never passed through `verify()`/`verifySubmission()`. The two systems run side by side, not together, this phase.
- **Real execution only happens in GitHub Actions CI, never on this project's own development machine.** This project's Windows development machine has no Docker, no `bitcoind`, no `lnd`, and no WSL2 distribution, so the full regtest stack cannot be run locally — every real execution of `npm run verify:cashu-real` happens on the `ubuntu-latest` GitHub Actions runner defined in `.github/workflows/real-cashu-integration.yml`. That execution is confirmed, not merely typechecked: [run 35853398175](https://github.com/TheWeirdDee/solvent/actions/runs/35853398175) (2026-09-23, commit `b22ed3a`) started a real Bitcoin Core 29.4 regtest node, two real `lnd` v0.21.3-beta nodes, and a real `cdk-mintd` v0.18.1, and printed `REAL CASHU FOUNDATION VERIFIED` followed by `REAL CASHU FOUNDATION RESTART PERSISTENCE VERIFIED` — a real Lightning payment with an observed preimage, real NUT-04/03/07/05 transitions, real double-spend rejection, and (after killing and restarting the mint process against the same on-disk SQLite database) 6/6 already-spent proofs still reporting SPENT with a post-restart double-spend attempt still refused. Evidence for that exact run is attached to the workflow run as the `real-cashu-evidence` artifact. See `docs/reproduce-real-stack.md` to reproduce it yourself.
- **Regtest, not mainnet.** Every coin involved is worthless by construction. No real-world Bitcoin, no real-world Lightning liquidity, at any point.
- **Single mint, single Lightning topology.** One `cdk-mintd`, two `lnd` nodes. CDK's own regtest environment exercises a larger topology (2 CLN + 2 LND + 2 mints); Phase 1 deliberately used the smallest stack that still proves every required transition (see `docs/dependencies.md`).
- **No CLN.** LND was used for both Lightning nodes specifically because it publishes Windows binaries and CLN does not — a decision driven by this project's own development environment, not a statement that CLN is less real or less suitable.

## What carries over unchanged, and remains real

Everything documented in `docs/trust-boundaries.md` from before this phase: real DLEQ/BIP-340 verification, real live Bitcoin Signet reserve queries, real live public Nostr relay publish/fetch, the real Gate 4 acceptance-boundary spy, the full 25/25 attack corpus, 264/264 deterministic tests, and the automated GitHub Pages deployment refresh. None of it was touched, weakened, or gutted by this phase — see "Preserve the existing verifier" in the Phase 1 instructions this document was written to satisfy, and `DECISIONS.md`.
